Membership purchase
design.

Glofox · One application, from request to recovery.

One modular Spring Boot application sells unlimited memberships and class packs. A persisted saga coordinates eligibility, resource holds, payment and activation through short database transactions. Unique claims, conditional inventory updates and saved request/payment identities protect competing and repeated requests. When payment becomes uncertain or local work stops, recovery uses recorded evidence to choose a safe next action. This walkthrough explains the implementation as it exists: an H2 demo and a local payment simulator, with explicit limits around durability and deployment.

02 / BUSINESS MODEL

Two products, different resource rules.

The service represents one studio. It identifies a member by a trimmed, lowercase name: " Alice " and "alice" share the same unlimited-membership claim. There is no member identity service, booking API, automatic expiry or cancellation workflow.

What this shows. Unlimited eligibility is a uniqueness rule; finite pack availability is a capacity rule. Neither is inferred from a successful payment. Resources are held first, then activated/consumed or safely released according to the recorded outcome.

Technical detail · the purchase contract

Create through POST /v1/memberships/purchases with a required Idempotency-Key and JSON fields memberName, planId and startDate. Amounts are integer cents; dates are calendar dates. A successful purchase or completed replay returns 201 with Location. X-Correlation-ID is optional and returned in responses. API reference.

A “commit” is a local transaction boundary. The gateway call is outside that boundary, even though the local simulator makes an independent ledger commit. Crash examples assume database rows survive an interrupted execution, as in integration tests; restarting the default H2 JVM resets the entire dataset.

What this shows. A purchase has several committed milestones. An HTTP error or missing purchase row does not prove that payment failed. The last saved saga, attempt and resource state decide what can safely happen next.

04 / CONSISTENCY

Two requests.
One authoritative decision.

Request identity, capacity and unlimited ownership are three distinct checks. The database enforces each decision; an in-memory mutex would not protect another application instance sharing that database.

The shared principle: unique inserts, conditional updates and atomic local commits are the business-integrity mechanisms. Optimistic versions protect stale workflow writes; they do not turn payment into a database transaction.
Technical detail · two independent retry budgets

Local optimistic-lock handling retries only recognized Spring/JPA optimistic conflicts, for three total attempts. Each reloads state inside a fresh REQUIRES_NEW transaction, with a short jittered delay. Exhaustion is a controlled 409. Synchronous payment retries separately allow three gateway calls for transient provider failures only. Business conflicts, declines and UNKNOWN outcomes are not blindly retried by either policy. Exact policy and transaction design.

What this shows. A replay should reuse its client key. A new key represents a new logical purchase and still competes for the same capacity or normalized member claim.

05 / PAYMENT SEMANTICS

A failed response is not always a failed charge.

The processor distinguishes a business decline, a technical outage and an uncertain outcome. It catches provider exceptions only around the gateway invocation; a later database failure cannot be mistaken for a new provider decline.

Compensate only when safe. Cleanup restores finite reserved capacity and/or removes the operation’s pending unlimited claim. It closes the failed workflow and client idempotency together. It does not refund a successful charge. UNKNOWN keeps resources held until reconciliation or manual review, because releasing them could allow a second purchase after the first was charged.

The client’s idempotency key identifies a logical request and its semantic payload. A separate, stable provider key is saved before charging and reused with the same amount. The simulated ledger returns its existing transaction for that key/amount; a different amount is rejected as an unresolved provider inconsistency. A real provider would need equivalent provider-side idempotency and reconciliation support.

What this shows. Retry is an opportunity to learn or complete the same payment, not permission to invent another payment identity. These guarantees describe the simulator; they do not establish exactly-once external financial effects.

06 / PERSISTED SAGA

Recovery follows evidence,
not a fresh purchase flow.

The in-memory fluent flow is single-use. Its milestones live in purchase_sagas, alongside payment and resource evidence. Recovery reads those rows and reuses safe finalization or compensation services; it does not restart the normal chain from the beginning.

What this shows. Confirmed success leads to finalization; definitive failure leads to cleanup. UNKNOWN can resolve either way, or stop at MANUAL_REVIEW. FAILED is safe pre-resource abandonment. Some entity-legal transitions are omitted here; the detailed state diagram is in the runtime guide.

The scheduler uses ShedLock with database time to coordinate scheduled batches. Selection requires a recoverable state, a due next-recovery time, enough inactivity and an available lease. A conditional, version-checked per-saga claim then protects that candidate, including programmatic recovery callers that do not use the scheduler lock. Default separate H2 JVMs share neither data nor locks.

Unresolved payment is reconciled with its existing provider key. Recovery finalizes a saved success without charging, compensates saved definitive failure, and defers further ambiguity with bounded backoff. After six total started payment attempts, unresolved work goes to manual review with holds and idempotency still pending. The worker has a bounded provider wait; its two-minute batch deadline stops admitting another saga, not the current execution. Neither lease expiry nor a timeout proves an external call stopped.

07 / FAULTS & EVIDENCE

Make the difficult paths reproducible.

The normal adapter and fault simulations use the same saved payment identity. The optional harness changes behavior at annotated method boundaries so declines, outages, uncertainty and activation failures can be explored without a real financial integration.

The local profile enables the harness application gate. Its versioned /internal/v1/admin/test-harness/settings API stores allow-listed overrides; an additional runtime master switch can disable injection. These are unauthenticated, trusted local/demo controls. Payment, inventory and membership activation each have operation-specific simulations.

For a non-NORMAL scenario, the aspect invokes the configured simulationMethod instead of the normal body. It passes the original arguments, exposes the selected scenario through thread-local context and clears that context afterward. The method is invoked reflectively on the target, so its own Spring AOP annotations are not applied by that call; transactional work stays in injected collaborators. 08 / DECISIONS & LIMITS

Deliberate boundaries.
Honest costs.

The implementation favors one understandable deployment with explicit persistence boundaries. Each choice solves a concrete failure mode and carries a cost.

What this demo does not claim

  • No durable recovery after default H2 JVM exit. The database and simulated provider ledger are both in memory.
  • No real payment integration or exactly-once external charge guarantee. The adapter is a local simulator.
  • No guaranteed automatic resolution of every unknown. Reconciliation is bounded; manual review retains unresolved resources. There is no public saga re-drive, refund, expiry or operator dashboard.
